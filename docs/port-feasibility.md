# Porting `Eurorackv1asym` from FeatureScript to CadQuery — feasibility

**Verdict: yes, it is possible — but it is a re-implementation, not a translation.**

Nothing in the model needs geometry CadQuery/OCCT cannot produce. Everything is
prismatic: rectilinear profiles, blind extrudes, booleans, linear patterns,
constant-radius fillets and equal-offset chamfers. There is no loft, sweep,
helix, draft, shell, variable fillet, or freeform surface anywhere in the export.

What does *not* survive the move is the way Onshape *refers* to geometry. That is
the whole cost of the job, and it is why the export cannot be mechanically
converted.

## What the export actually contains

Generated by `tools/fs_inventory.py`; full dump in `docs/inventory.txt`.

| | count |
|---|---|
| features | 118 |
| — variable assignments (`assignVariable`) | 35 |
| — sketches | 20 |
| — extrudes | 28 |
| — booleans | 6 |
| — linear patterns | 6 |
| — fillets / chamfers | 4 / 3 (one fillet is dead) |
| — split parts / mirrors | 3 / 2 |
| — holes | 3 |
| — transforms | 4 |
| — construction planes / mate connectors | 2 / 2 |
| sketch entities | 148 lines, 30 points, 8 circles |

| — of which are *driving dimensions* | 54 |

## What ports cleanly

**The variable table.** 35 variables, all scalar lengths or counts, with
readable expressions preserved in the export (`#BottomHoleInset+(.7*#BoltCounterboreDiam)`).
These become a Python dataclass or plain module constants. Direct, mechanical.

**Sketch profiles.** 435 constraints looks alarming, but only 54 of them are
driving dimensions — the rest are coincident/parallel/perpendicular/mirror
constraints that exist because Onshape needs a solver and CadQuery does not. In
CadQuery you write the solved coordinates as a `polyline`, and "parallel" is a
consequence of the coordinates rather than a constraint to satisfy. There is
exactly one `TANGENT` constraint in the entire model.

**Sketch planes.** All 20 sketches sit on either a default plane (`Right`, `Top`)
or a planar face of an earlier extrude — and the export records *which sketch
edge generated that face*. So every plane is reconstructible arithmetically from
the parameters; none depends on a fillet face, a swept face, or anything whose
position is hard to predict.

**Extrudes, booleans, patterns, mirrors, splits, holes.** One-to-one with
`extrude` / `cut` / `union` / `intersect`, list comprehensions over translated
copies, `mirror`, and `Workplane.hole`. The holes are plain blind holes
(Ø3.2×3.5 and Ø2×2.7; a third, Ø2×5, is dead — see below) — no counterbore,
countersink, or thread, despite the `hole()` feature carrying Onshape's full
tapping parameter block.

## What has to be rebuilt by hand

**The 278 `qCompressed` queries.** These are Onshape's topological-naming
references. Decompressed, one reads:

```
QueryM5 disambiguationData[ disambiguationType TOPOLOGY entities[
  derivedFrom{ entityType EDGES historyType CREATION
               operationId F3HD5PxY3AAr9PG_3wireOp
               queryType SKETCH_ENTITY sketchEntityId IAhQH5pdcXoa0.MirrorCS }
  imprint IMPRINT ... ]]
```

That is "the edge produced by imprinting the mirrored sketch entity
`IAhQH5pdcXoa0` from the rail block profile sketch." CadQuery has no persistent
naming and no equivalent concept. Every one of these has to be replaced by a
geometric selector (`>Z`, `|Y`, `NearestToPointSelector`, a box selector, or a
lambda over edge midpoints).

This is the real work, and it concentrates in the fillet/chamfer features —
6 live ones selecting 20 edges between them. The rest of the queries pick sketch regions
and extrude targets, where the substitute is usually just "build that profile as
its own `Workplane`."

**Region selection.** Several sketches are extruded region-by-region with
different depths — the end-cap profile sketch `FNqrsvGVGM0ZkbD_3` alone feeds
eight extrudes at 25 and 35 mm. Onshape splits a sketch into regions
automatically where lines cross; CadQuery does not. Each region has to be
authored as a separate closed profile.

**`BaseCase` is a measured variable.** It is `VariableMode.MEASURED` — its value
comes from measuring the model, and the export literally stores `"?"` for it.
`BaseCaseInset = #BaseCase - 3*#CaseFrontBackThickness` depends on it. This has
to be re-derived analytically (or read back with a bounding-box query mid-build).

**`TransformType.TRANSFORM_MATE_CONNECTORS`.** One transform positions a body by
mapping one mate connector onto another. CadQuery has no mate connectors; this
becomes an explicit `cq.Location` computed from the same reference geometry.

**Configuration-driven branching.** Four features are switched on by the Top Lips
and Bottom Lips enums — `Fillet 1` / `Chamfer 1` for the top, `Lower Edges
Fillet` / `Lower Lip Chamf` for the bottom. These become `if` branches on the
enum value, as in the spike.

## What does not need porting at all

Four features are hard-suppressed (`if (false)`): `endcap tab sizing`,
`Sketch 3`, `PSU mounts`, `Extrude 6`. The PSU mounting provisions belong to an
older revision of the design and are not wanted.

Suppression propagates, and silently — the export wraps every feature call in
`try(...)`, so a live feature that references suppressed geometry simply fails
and is swallowed. Six more features are dead for that reason:

| feature | why |
|---|---|
| `Extrude 4` | consumes `Sketch 3` |
| `Extrude 5` | consumes `PSU mounts` |
| `Sketch 5` | placed on a face of `PSU mounts` |
| `Fillet 4` | rounds edges created by `Sketch 5` |
| `Sketch 7` | placed on a face of `PSU mounts` |
| the Ø2×5 hole | located from `Sketch 7` |

So 10 of 118 features are dead weight, including one of the four fillets and one
of the three holes. Skipping them takes the fillet/chamfer count that needs
hand-written edge selectors from 7 to 6, and the holes from 3 to 2.
`tools/fs_inventory.py` computes this list, so it stays accurate if the model is
re-exported.

## Spike

`poc/spike_case_shell.py` exercises the three mechanics that have no direct
equivalent — hand-written slanted profile, parameter-driven extrude length, and
subset edge selection for the fillet/chamfer enum — on CadQuery 2.8.0:

```
sharp    valid=True volume= 200.99 cm3 faces= 12 edges= 24 bbox=128.50 x 132.08 x 62.40 mm
round    valid=True volume= 200.77 cm3 faces= 14 edges= 30 bbox=128.50 x 132.08 x 62.40 mm
chamfer  valid=True volume= 200.47 cm3 faces= 14 edges= 30 bbox=128.50 x 132.08 x 62.40 mm
STEP export OK
```

All three lip variants build a valid solid and export to STEP. The selector
`.edges("|Y").edges(">Z")` picks exactly the intended 2 edges. It is a stand-in
shape, not the real case wall.

## Suggested approach

1. Port the variable table verbatim. Cheap, and it makes everything downstream readable.
2. Rebuild the two root sketches — `Case profile` (10 entities) and
   `Rail block profile` (50 entities) — as parametric functions returning
   `Workplane` profiles. These drive most of the model.
3. Build the case body, end caps, and rails as separate functions returning
   solids, assembled with booleans, rather than mirroring Onshape's flat
   feature-by-feature order. The Onshape ordering is an artifact of interactive
   modelling and reproducing it faithfully would make the Python harder to read
   than the geometry warrants.
4. Do the fillets and chamfers last, with named selector helpers, and assert the
   selected edge count in each — a silently-wrong selector is the most likely
   defect in a port like this, and an `assert n == 4` catches it at the parameter
   values where it breaks.
5. Validate against Onshape by exporting STEP from both at matched parameter
   values and comparing volume, bounding box, and face/edge counts. Do this
   across the parameter range, not just at the default — the fillet selectors
   are the thing that will break when `Front_Height` or `HP_Count` moves.

## Cost and risk

Roughly 700–1000 lines of CadQuery. The bulk is transcribing profile coordinates
and re-deriving the ~24 fillet/chamfer edge selections; neither is difficult,
both are tedious and want checking against the original.

The one thing to decide up front: **how faithful does the port need to be?**
Matching the Onshape output to within a tolerance across the whole parameter
range is materially more work than producing a clean parametric case that makes
the same parts. If the goal is a usable parametric Eurorack case in Python, the
second is the better target and roughly half the effort.

## Reproducing this analysis

```
pip install cadquery
python3 tools/fs_inventory.py reference/Eurorackv1asym.fs   # regenerates docs/inventory.txt
python3 poc/spike_case_shell.py
```
